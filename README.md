# wmoop.py

**The Python reference binding of [WMOOP](https://github.com/WMOOP) — *World Map
Object-Oriented Programming*.**

This is the **Python twin** of [`wmoop.net`](https://github.com/WMOOP/wmoop.net): the *same*
World Model — same domains, same cross-domain `Person`→`Driver` example, same design patterns —
re-expressed in idiomatic Python. It exists to prove the project's central claim: a single,
language-neutral model maps to any language **without duplicating the concepts**, only re-stating
them in each language's idioms.

> The canonical model and all design documents live in
> [`wmoop.doc`](https://github.com/WMOOP/wmoop.doc). The data classes here are **generated** from
> the WML model by [`wmoop.tools`](https://github.com/WMOOP/wmoop.tools); this repo adds only the
> behaviour, the design patterns, the demos and the runner of the shared conformance vectors.

## Parity with the C# binding

| Concept | C# (`wmoop.net`) | Python (`wmoop.py`) |
|---------|------------------|---------------------|
| Generated data classes | one project per domain, a `partial class` per concept | one module per domain in the `wmoop` namespace package |
| Hand-written behaviour | the other half of the `partial` class | a `<Name>Ext` mixin in `wmoop_ext.<domain>` |
| Construction | `required` / `init` properties, object initializers | keyword-only arguments |
| Value objects | `readonly struct` | `@dataclass(frozen=True)` |
| Roles by composition | `AddRole` / `GetRole<T>()` | `add_role` / `get_role(T)` |
| Relations, inverse kept in step | `Links<T>` and property setters | `LinkSet` and `One` / `Many` descriptors |
| Visitor hook | interface `IAreaVisitor` | `typing.Protocol` (`AreaVisitor`) |
| Specification combinators | `.And()/.Or()/.Not()` | `&` / `\|` / `~` dunder operators |
| Generics | `ISpecification<T>` | `Generic[T]` |
| Conformance | `Wmoop.Tests` runs the shared vectors of `wmoop.doc` | `conformance.py` runs the same vectors |

Same semantics, idiomatic surface. That is exactly the "write once, replicate everywhere" story.

## Layout

```
wmoop.py/
├── generated/              # GENERATED by wmoop.tools from the pinned model; never hand-edited
│   ├── wmoop/              # the wmoop namespace package: _kernel.py + one module per domain
│   └── WMOOP_SOURCE.json   # the wmoop.doc / wmoop.json / wmoop.tools commits it came from
├── wmoop/
│   └── patterns.py         # wmoop.patterns: Visitor, Specification, Builder, Strategy, Registry
├── wmoop_ext/              # behaviour mixed into the generated classes
│   ├── nature.py           # PersonExt.age_on
│   ├── transport.py        # describe / classification per vehicle kind, DriverExt.can_drive
│   └── geography.py        # AreaVisitor; total_population and accept on the areas
├── demo.py                 # cross-domain roles + polymorphism walkthrough
├── patterns_demo.py        # one section per design pattern, self-checking
├── conformance.py          # runs the shared conformance vectors from external/wmoop.doc
└── external/               # git submodules: wmoop.doc (the model), wmoop.tools (the generator)
```

`wmoop` is a namespace package (PEP 420), with no `__init__.py`. `generated/wmoop/` holds the
generated modules, and `wmoop/` adds the hand-written `wmoop.patterns`. The scripts put
`generated/` and the repository root on `sys.path`; your own code needs both as well.

## Run

Requires **Python 3.10+**. No third-party dependencies. The conformance vectors come from the
`external/wmoop.doc` submodule, so clone with `--recurse-submodules` (or run
`git submodule update --init`).

```bash
python demo.py
python patterns_demo.py
python conformance.py  # the shared conformance vectors; exits non-zero on failure
```

(On Windows the launcher is usually `py` instead of `python`.)

## Conformance

The checks are not written here. They are the shared conformance vectors of
[`wmoop.doc/conformance`](https://github.com/WMOOP/wmoop.doc/tree/main/conformance), written once
as data and run by every binding, so `wmoop.py` and `wmoop.net` provably agree.
[`conformance.py`](conformance.py) reads the bundle `external/wmoop.doc/conformance/suite.json`:

- A model type resolves through the generated `WM_ID`.
- A model name such as `wheelCount` matches the member `wheel_count`.
- An error matches by its registry code (`WmoopError.code`).
- Python itself refuses a call that leaves out a keyword-only argument without a default. The
  runner reports that as the model's `WM-REQUIRED-MISSING`.

A `pending` vector describes a rule the model has and no binding enforces yet. It is reported
but does not fail the run. Because the vectors are pinned with the model, a regeneration that
brings new vectors also runs them. To add or change a check, add a vector in `wmoop.doc`, not a
test here.

## Generated binding

`generated/wmoop/` is generated by [`wmoop.tools`](https://github.com/WMOOP/wmoop.tools) from the
canonical model in [`wmoop.doc`](https://github.com/WMOOP/wmoop.doc). Both repos are pinned as git
submodules, `external/wmoop.doc` and `external/wmoop.tools`, and `generated/WMOOP_SOURCE.json`
records the exact commits it was generated from.

Each generated class puts the mixin `<Name>Ext` from `wmoop_ext.<domain>` first among its bases,
when there is one. The mixin overrides the generated chain and is inherited down it:

```python
# generated/wmoop/transport.py: generated, never edited
class Moped(*ext('transport', 'Moped'), Motorcycle):
    ...

# wmoop_ext/transport.py: hand-written
class MopedExt:
    @property
    def classification(self) -> str:
        return "moped"
```

- **Never edit `generated/` by hand.** CI regenerates it from the pins and fails on any difference.
  - To change data, change the model in `wmoop.doc` (or the generator in `wmoop.tools`).
  - To add behaviour, add or extend a `<Name>Ext` mixin in `wmoop_ext/<domain>.py`.
  - A mixin module is imported while its generated module loads, so it imports generated classes
    only under `TYPE_CHECKING`.
- **Regeneration is automatic.** When `wmoop.doc` or `wmoop.tools` changes, and daily,
  [`regen.yml`](.github/workflows/regen.yml) moves both pins to upstream `main`, regenerates, runs
  the tests and opens (or updates) one `chore(regen): …` pull request.
- **To regenerate by hand** after moving a pin, you need Python 3.10+ and
  `pip install -r external/wmoop.doc/schema/requirements.txt`:

  ```bash
  git submodule update --init                        # external/wmoop.doc, external/wmoop.tools
  git -C external/wmoop.doc submodule update --init  # the grammar the model validator reads
  python external/wmoop.tools/tools/regen_binding.py --lang python
  ```

Sometimes the model changes in a way a mixin relies on, for example a renamed property. The
regeneration run then fails its tests and opens no pull request. A human moves the pins on a
branch, regenerates and updates the mixin. Generated code never needs a manual edit
([docs/03-architecture.md §4.4](https://github.com/WMOOP/wmoop.doc/blob/main/docs/03-architecture.md)).
